# Version 2 and beyond

Version 1 is deliberately **single-roster**, but a roster may have **multiple
contracts**. Each contract owns its own state; MMR may live in one or more of
the roster's contracts, and the platform does not prescribe a single ranking
contract. Matchmaking runs outside the contracts, and the contracts only
consume results. What v1 does not do is share state across rosters. This
document keeps the deferred ideas in one place so v1 can stay small.

Nothing here is a commitment or a stable API. The ordering is a suggestion.

## 1. Cross-roster and global MMR

V1 stores MMR in whichever contract(s) the roster chooses. A roster can have a
dedicated ranking contract, keep MMR beside the roster state, or split it; the
platform does not care. A player can be high in one roster and low in another,
which is the intended behaviour.

V2 could add:

- a shared **ranking contract** that owns a global MMR and exposes a view;
- roster contracts that subscribe to that contract's updates;
- a per-player/per-roster override, so a global ladder can coexist with
  roster-local rules;
- a migration path from per-roster MMR to a shared ladder without replaying
  every old match.

This needs cross-contract calls (or a platform event dispatch) first. It is
not needed while rosters are disjoint.

## 2. Contract listeners and the event bus

The source contract emits a committed event; a dispatcher delivers it to
listener contracts after the source transaction commits.

```ts
type ContractListener = {
  sourceContractId: string;
  event: string;
  targetContractId: string;
  endpoint: string;
  filter?: JsonValue;
  active: boolean;
};
```

Design rules:

- **Asynchronous delivery after commit.** Never call listeners inside the
  source transaction: a listener failure must not roll back the source, and
  synchronous fan-out invites reentrancy and loops.
- **At-least-once, idempotent.** Every delivery carries a stable `eventId`;
  the listener de-dupes. Retries and a dead-letter state are part of the
  dispatcher, not the listener.
- **Bounded.** Cap hops, fan-out, and retries; disable a listener after
  repeated failures.
- **Paid by the listener.** A listener's owner pays for its own endpoint; a
  listener cannot drain the source.
- **Optional for correctness.** With lazy resolve, a roster contract can read
  the current MMR at resolve even if it missed an event. Listeners are for
  caches and reactive integrations, not the only path to correctness.

The registry can live in the platform. An on-chain emitter contract can keep
the same schema for discoverability, but the actual delivery should still be
asynchronous.

## 3. Third-party applications

The flow is:

```text
contract emits MatchReported
        │
        ▼
third party listens (WebSocket, or polls /events)
        │
        ▼
third party calls the same endpoint the owner could call
        │
        ▼
platform verifies the owner's grant; owner pays
```

A third party does **not** need its own caller kind or access mode. It acts as
the owner:

```ts
ctx.msgSender = { kind: "human", id: ownerId };
ctx.txOrigin  = { kind: "human", id: ownerId, delegate: "<clientId>" };
```

The owner creates a grant for the app; the app authenticates with that grant
and calls the normal `human`/`public` endpoints the owner could call. A
`roster-lock` or `contract` endpoint remains off limits. The contract can use
`txOrigin.delegate` for audit, but access is ordinary human access.

### Records and scopes

- The call log and event rows record the owner as the caller plus the delegate
  `clientId`; the user can see what the app did.
- The grant scopes are a nested whitelist:

```ts
type ApiKeyScope = {
  rosters: Record<RosterId, {
    contracts: Record<ContractId, EndpointName[]>;
  }>;
};
```

  The platform checks the target roster, contract and endpoint before calling.
  There are no wildcards; a key with no matching entry is denied. Scopes can
  span rosters, but each must be listed explicitly.
- The key belongs to the user, is hashed at rest, has an expiry, and can be
  revoked. The owner pays; the third party needs no wallet or node.
- The key can only reach `human`/`public` endpoints as that user. It cannot
  reach `roster-lock` or `contract` endpoints.
- The contract may keep its own trusted-client allowlist, but the platform grant
  is the primary gate.
- Full OAuth is justified for a marketplace of third-party apps. For a handful
  of integrations, owner-created scoped tokens are simpler and just as
  revocable.

### Events for third parties

- The third party subscribes to the contract's committed events over a
  WebSocket, or falls back to `GET /events?after=`.
- Events are the trigger; the app's call is the action. Event rows carry the
  delegate id alongside the owner.
- Idempotency is by `matchId`/`eventId`, so a reconnect or retry cannot apply
  the same result twice.
- A third party that sees private/roster-scoped events needs the grant to cover
  the subscription, not just the write endpoint.

## 4. Third-party matchmaking

Matchmaking should stay **outside** the contract. The contract stores MMR and
results; it does not pair players or wait in a queue. See
[matchmaking-marketplace.md](matchmaking-marketplace.md) for the executable
matchmaker marketplace; the notes below are specifically about third-party
services.

Recommended split:

- **Official options (curated):** a small set of algorithms the platform runs
  off-chain (for example 1v1 Elo/Glicko, team average, free-for-all placement).
  The contract receives `mmrAfter` and applies it. Gas pays for the update, not
  for the matchmaking computation.
- **Custom/third-party options:** an owner-granted app reports the same
  `MatchReported`/`mmrAfter` shape as the owner. The owner opts in per roster;
  the platform does not promise queue quality, latency, or data correctness.
- **No global open marketplace in v1.** Long waits, unbalanced matchups, and
  bad data are service-quality problems; opening the platform to arbitrary
  matchmakers turns them into trust and abuse problems too. Start with curated
  presets and a small set of allowlisted third parties.

The contract's `reportMatch` input can carry `mmrAfter` and a `service` id.
That keeps the contract independent of the matchmaking algorithm and lets the
owner switch services without redeploying the roster.

## 5. Ownership and profit sharing

V1 already supports multiple contracts per roster. Ownership is application
data stored at `init`. It can be transferred by a contract endpoint, but the
platform's deploy owner (who may replace the code) is separate.

V2 could add:

- a platform-level ownership transfer (or immutable/controlled contracts) so
  selling a roster transfers the right to redeploy;
- a shared treasury across a roster's contracts;
- profit-sharing rules as contract state, not platform policy;
- delegated administration scoped separately from code ownership.

## 6. Event retention and replay

V1 keeps every event and a call summary, but not call inputs/results.

V2 candidates:

- event retention and archival;
- an opt-in call archive (input, result, source hash) for replay/audit;
- a source-hash/version archive per deploy, so old events can be decoded after
  a schema change;
- a read-model rebuild tool.

## Non-goals for v1

- On-chain matchmaking.
- A global open third-party marketplace.
- Synchronous cross-contract fan-out.
- A shared MMR across rosters.
- A new `delegate` caller kind; the app acts as the owner.
- Full OAuth; a scoped, revocable owner grant is enough to start.
- Exactly-once event delivery; at-least-once plus idempotency is the model.
